## 4. Staff-Level Project Story: Model Foundry

### Context

Model owners had to visit multiple tools to answer basic operational questions:

- Is the model active?
- Is inference occurring?
- Are features available?
- Is offline data fresh?
- Who owns the model?
- Is compliance metadata complete?
- What changed recently?

The systems had different schemas, latency characteristics, and definitions of health.

### Problem

The frontend was not simply a dashboard problem.

The real problem was:

> How do we provide a trustworthy decision-making experience when the underlying data is distributed, slow, occasionally stale, and only partially available?

### Your Role

Describe yourself as the person who drove:

- Information architecture.
- Frontend data contracts.
- Common entity models.
- Loading and failure semantics.
- Performance instrumentation.
- Reusable components.
- Cross-team adoption.
- API and frontend performance improvements.

### Key Technical Decisions

#### 1. Progressive Rendering Instead of Waiting for Every Backend

Render the critical identity and summary information first, followed by independent sections.

```tsx
function ModelPage({ modelId }: { modelId: string }) {
  return (
    <PageShell>
      <ModelIdentity modelId={modelId} />

      <SectionErrorBoundary title="Model health">
        <Suspense fallback={<HealthSummarySkeleton />}>
          <ModelHealthSummary modelId={modelId} />
        </Suspense>
      </SectionErrorBoundary>

      <SectionErrorBoundary title="Feature health">
        <Suspense fallback={<FeatureTableSkeleton rows={8} />}>
          <FeatureHealthTable modelId={modelId} />
        </Suspense>
      </SectionErrorBoundary>

      <SectionErrorBoundary title="Lineage">
        <Suspense fallback={<LineageSkeleton />}>
          <ModelLineage modelId={modelId} />
        </Suspense>
      </SectionErrorBoundary>
    </PageShell>
  );
}
```

Staff-level explanation:

> I avoided a single page-level request because the slowest or least reliable dependency would control the entire experience. Independent boundaries let us prioritize critical information, isolate failure, and measure each section separately.

#### 2. Distinguish Unavailable, Unhealthy, Stale, and Unknown

A major observability mistake is treating missing information as failure.

```ts
type HealthState =
  | { kind: 'healthy'; measuredAt: string }
  | { kind: 'degraded'; measuredAt: string; reasons: string[] }
  | { kind: 'unhealthy'; measuredAt: string; reasons: string[] }
  | { kind: 'stale'; measuredAt: string; expectedFreshnessMinutes: number }
  | { kind: 'unavailable'; reason: 'not_configured' | 'permission_denied' }
  | { kind: 'unknown'; reason: 'request_failed' | 'insufficient_data' };
```

Explain:

> “Unhealthy” is a domain result. “Unknown” is a system result. Combining them causes users to react incorrectly and undermines trust in the product.

#### 3. Treat Freshness as Part of the Contract

```ts
interface DataEnvelope<T> {
  data: T;
  generatedAt: string;
  source: string;
  freshness: {
    state: 'fresh' | 'aging' | 'stale';
    maxAgeSeconds: number;
  };
  requestId: string;
}
```

This supports:

- Honest UI timestamps.
- Stale-while-revalidate.
- Debugging.
- Source attribution.
- Incident investigation.
- Consistent freshness indicators.

#### 4. Keep Shareable State in the URL

For large observability tables, filters should survive reloads and be shareable.

```tsx
type FeatureFilters = {
  status?: 'healthy' | 'degraded' | 'unhealthy';
  environment?: 'online' | 'offline';
  query?: string;
  page?: number;
};

function useFeatureFilters(): [FeatureFilters, (patch: Partial<FeatureFilters>) => void] {
  const [params, setParams] = useSearchParams();

  const filters: FeatureFilters = {
    status: params.get('status') as FeatureFilters['status'],
    environment: params.get('environment') as FeatureFilters['environment'],
    query: params.get('q') ?? undefined,
    page: Number(params.get('page') ?? 1),
  };

  const updateFilters = (patch: Partial<FeatureFilters>) => {
    const next = new URLSearchParams(params);

    for (const [key, value] of Object.entries(patch)) {
      const paramName = key === 'query' ? 'q' : key;

      if (value === undefined || value === '') {
        next.delete(paramName);
      } else {
        next.set(paramName, String(value));
      }
    }

    setParams(next, { replace: true });
  };

  return [filters, updateFilters];
}
```

Staff-level rationale:

> URL state made investigations reproducible. Engineers could send a filtered view to an on-call engineer rather than describing the exact filters manually.

## 5. Shareable Components and EngX

Do not present shared components as merely publishing a component library. Describe the full adoption system.

### Example Shared Component: `EntityHealthSummary`

Multiple pages may need:

- Entity identity.
- Ownership.
- Environment.
- Health.
- Last activity.
- Freshness.
- Primary actions.

```tsx
type HealthTone = 'positive' | 'warning' | 'critical' | 'neutral';

interface EntityHealthSummaryProps {
  title: string;
  subtitle?: string;
  owner?: {
    label: string;
    href?: string;
  };
  health: {
    label: string;
    tone: HealthTone;
    description: string;
  };
  lastUpdated?: string;
  actions?: React.ReactNode;
}

export function EntityHealthSummary({
  title,
  subtitle,
  owner,
  health,
  lastUpdated,
  actions,
}: EntityHealthSummaryProps) {
  return (
    <section aria-labelledby="entity-title">
      <div>
        <h1 id="entity-title">{title}</h1>
        {subtitle && <p>{subtitle}</p>}

        {owner && (
          <p>Owned by {owner.href ? <a href={owner.href}>{owner.label}</a> : owner.label}</p>
        )}
      </div>

      <div>
        <StatusBadge tone={health.tone}>{health.label}</StatusBadge>
        <p>{health.description}</p>

        {lastUpdated && (
          <p>
            Updated <time dateTime={lastUpdated}>{formatRelativeTime(lastUpdated)}</time>
          </p>
        )}
      </div>

      {actions && <div aria-label="Entity actions">{actions}</div>}
    </section>
  );
}
```

### Staff-Level API Design Decisions

Explain why the component:

- Accepts domain-neutral display data.
- Does not fetch data internally.
- Uses semantic status values rather than raw colors.
- Allows links without requiring routing-library coupling.
- Exposes actions through composition.
- Keeps domain transformations outside the visual component.

Avoid this:

```tsx
<ModelHeader modelId={modelId} />
```

if the component secretly fetches five model-specific services.

Prefer:

```tsx
<EntityHealthSummary
  title={model.displayName}
  owner={toOwnerViewModel(model.owner)}
  health={toHealthViewModel(model.health)}
  lastUpdated={model.generatedAt}
/>
```

This keeps the shared component usable for models, datasets, features, jobs, and pipelines.

### EngX Strategy

#### Discover

Audit existing surfaces and identify repeated problems:

- Slightly different health badges.
- Different timestamp formatting.
- Inconsistent empty states.
- Duplicate table filtering.
- Different loading and error semantics.
- Accessibility gaps.

#### Standardize Semantics Before Visuals

Define:

- What “stale” means.
- Which health states exist.
- Required accessible labels.
- Timestamp conventions.
- Retry behavior.
- Analytics events.

#### Build with Reference Consumers

Do not create an abstract platform first.

Start with two real consumers that are similar enough to share infrastructure but different enough to test extensibility.

#### Make Adoption Inexpensive

Provide:

- TypeScript APIs.
- Storybook examples.
- Accessibility tests.
- Migration recipes.
- Codemods where useful.
- Clear ownership.
- Versioning and deprecation guidance.

#### Measure Platform Success

Track:

- Number of consuming surfaces.
- Time to build a new entity page.
- Duplicate component reduction.
- Accessibility violations.
- Frontend error rates.
- Performance regressions.
- Support requests.
- Percentage of usage on the current version.

A strong Staff statement:

> The measure of a shared component is not that it exists. It is that teams voluntarily adopt it because it is easier, safer, and faster than building their own version.

## 6. Frontend Reliability

### Section-Level Failure Isolation

```tsx
type ErrorBoundaryProps = {
  title: string;
  children: React.ReactNode;
};

type ErrorBoundaryState = {
  error: Error | null;
};

class SectionErrorBoundary extends React.Component<ErrorBoundaryProps, ErrorBoundaryState> {
  state: ErrorBoundaryState = { error: null };

  static getDerivedStateFromError(error: Error): ErrorBoundaryState {
    return { error };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportFrontendError({
      error,
      componentStack: info.componentStack,
      section: this.props.title,
    });
  }

  retry = () => {
    this.setState({ error: null });
  };

  render() {
    if (this.state.error) {
      return (
        <section role="alert">
          <h2>{this.props.title} is temporarily unavailable</h2>
          <p>Other information on this page is still available.</p>
          <button type="button" onClick={this.retry}>
            Try again
          </button>
        </section>
      );
    }

    return this.props.children;
  }
}
```

Discuss:

- Do not let lineage failure hide model identity.
- Preserve successfully loaded information.
- Provide a local retry.
- Report the section and request ID.
- Avoid exposing raw errors to users.
- Announce meaningful failures accessibly.

### Prevent Stale Request Races

```ts
function useModelSearch(query: string) {
  const [state, setState] = useState<{
    status: 'idle' | 'loading' | 'success' | 'error';
    results: ModelSummary[];
  }>({
    status: 'idle',
    results: [],
  });

  useEffect(() => {
    if (!query.trim()) {
      setState({ status: 'idle', results: [] });
      return;
    }

    const controller = new AbortController();

    setState((current) => ({
      ...current,
      status: 'loading',
    }));

    searchModels(query, { signal: controller.signal })
      .then((results) => {
        setState({
          status: 'success',
          results,
        });
      })
      .catch((error) => {
        if (error.name === 'AbortError') return;

        setState((current) => ({
          ...current,
          status: 'error',
        }));
      });

    return () => controller.abort();
  }, [query]);

  return state;
}
```

Explain:

> Without cancellation or request identity, an older slow response can overwrite a newer response. This is especially common in search, filters, and time-range controls.

### Retry Only Safe Operations

```ts
async function fetchWithRetry<T>(
  operation: () => Promise<T>,
  options: {
    attempts?: number;
    baseDelayMs?: number;
    shouldRetry?: (error: unknown) => boolean;
  } = {}
): Promise<T> {
  const { attempts = 3, baseDelayMs = 250, shouldRetry = isTransientError } = options;

  let lastError: unknown;

  for (let attempt = 0; attempt < attempts; attempt += 1) {
    try {
      return await operation();
    } catch (error) {
      lastError = error;

      const isLastAttempt = attempt === attempts - 1;
      if (isLastAttempt || !shouldRetry(error)) throw error;

      const exponentialDelay = baseDelayMs * 2 ** attempt;
      const jitter = Math.random() * 100;

      await sleep(exponentialDelay + jitter);
    }
  }

  throw lastError;
}
```

Staff-level nuance:

- Retry idempotent reads.
- Do not blindly retry mutations.
- Respect server retry hints.
- Avoid synchronized retries.
- Cap attempts.
- Surface degraded state.
- Instrument retry counts.

### Reliability Metrics

Mention metrics such as:

### Lazy-Load Expensive Visualizations

```tsx
const LineageGraph = lazy(() => import('./LineageGraph'));

function LineageSection({ graph }: { graph: LineageData }) {
  const [isExpanded, setExpanded] = useState(false);

  return (
    <section>
      <button
        type="button"
        aria-expanded={isExpanded}
        onClick={() => setExpanded((value) => !value)}
      >
        Model lineage
      </button>

        <Suspense fallback={<LineageSkeleton />}>
          <LineageGraph graph={graph} />
        </Suspense>
      )}
    </section>

```

Explanation:

> The lineage graph is valuable, but it should not delay the health summary for every user. I would load it when the section becomes visible or when the user expands it.

### Memoize the Correct Boundary

```tsx
const FeatureRow = memo(function FeatureRow({
  feature,
  onSelect,
}: {
  feature: FeatureSummary;
  onSelect: (featureId: string) => void;
}) {
  return (
    <tr>
      <td>
        <button type="button" onClick={() => onSelect(feature.id)}>
          {feature.name}
        </button>
      </td>
      <td>{feature.healthLabel}</td>
      <td>{feature.lastSeenLabel}</td>
    </tr>
  );
});
```

Memoization is useful only when:

- Row rendering is meaningful.
- Props remain stable.
- Parent rerenders frequently.
- Profiling shows render cost.

Do not claim `useMemo` automatically improves performance.

### Defer Noncritical Filtering Work

```tsx
function FeatureExplorer({ features }: { features: FeatureSummary[] }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);

  const filteredFeatures = useMemo(() => {
    const normalized = deferredQuery.trim().toLowerCase();

    if (!normalized) return features;

    return features.filter((feature) => feature.name.toLowerCase().includes(normalized));
  }, [features, deferredQuery]);

  return (
    <>
      <label>
        Search features
        <input value={query} onChange={(event) => setQuery(event.target.value)} />
      </label>

      <FeatureTable features={filteredFeatures} />
    </>
  );
}
```

### Virtualize Large Datasets

For several hundred simple rows, pagination may be more accessible and operationally simpler. For thousands of interactive rows where continuous scrolling is important, use virtualization, stable row keys, overscan, and careful focus handling.

Trade-offs:

- Better rendering performance.
- More complicated keyboard navigation.
- Browser find may not see unloaded rows.
- Dynamic row height is harder.
- Screen-reader behavior requires testing.
- Printing and exporting require separate paths.

### Your Performance Story

Use this format:

> We had a high-value model workflow taking approximately 12–15 seconds. I first added route and dependency-level measurements so we could separate network, aggregation, and rendering time. We found that the page waited for several independent datasets and repeatedly fetched information that could be aggregated or cached.
>
> We changed the experience to prioritize critical model information, parallelized independent data access, reduced redundant calls, improved backend aggregation, and rendered secondary sections progressively. We also added regression measurements by route.
>
> That reduced the workflow to under four seconds. More importantly, we turned the work into reusable guidance and primitives so other pages would not reproduce the same waterfall.

## 8. Accessibility

Airbnb is a consumer marketplace, so accessibility should be integrated into every design answer.

### Semantic Structure

- One clear page heading.
- Logical heading hierarchy.
- Tables for tabular information.
- Buttons for actions.
- Links for navigation.
- Labels for controls.
- `time` elements for timestamps.

### Status Communication

Do not communicate health only through color.

```tsx
function StatusBadge({ status }: { status: 'healthy' | 'warning' | 'critical' }) {
  const labels = {
    healthy: 'Healthy',
    warning: 'Needs attention',
    critical: 'Critical',
  };

  return (
    <span data-status={status}>
      <StatusIcon status={status} aria-hidden="true" />
      <span>{labels[status]}</span>
    </span>
  );
}
```

### Async Updates

```tsx
function SearchStatus({ loading, resultCount }: { loading: boolean; resultCount: number }) {
  return (
    <div role="status" aria-live="polite" aria-atomic="true">
      {loading ? 'Searching models' : `${resultCount} models found`}
    </div>
  );
}
```

Avoid announcing every network state change or every streamed update.

### Charts

A chart should have:

- A concise summary.
- Current value.
- Trend description.
- Accessible data table or downloadable representation.
- No color-only distinctions.

## 11. Staff-Level System Design Framework

### 1. Clarify the Experience

- Primary users.
- Core tasks.
- Devices.
- Accessibility.
- SEO.
- Offline expectations.
- Collaboration or sharing.
- Freshness.

### 2. Define Success

- User metrics.
- Reliability target.
- Performance target.
- Accessibility target.
- Engineering adoption target.

### 3. Draw the Architecture

```text
Browser
  ├── Application shell
  ├── Route controller
  ├── Server-state cache
  ├── Shared experience components
  ├── Feature modules
  ├── Analytics and observability
  └── Error boundaries

Web/BFF
  ├── UI-oriented aggregation
  ├── Authentication and authorization
  ├── Schema normalization
  ├── Caching
  └── Partial-response metadata

Domain services
  ├── Model metadata
  ├── Health
  ├── Feature telemetry
  ├── Ownership
  ├── Compliance
  └── Lineage
```

### 4. Explain State Ownership

- URL: shareable filters, selected entity, date range.
- Server cache: fetched domain data.
- Local component state: expanded rows, open dialogs.
- Form state: drafts and validation.
- Global client state: only genuinely cross-route UI state.

### 5. Deep Dive

Choose two or three:

- Performance.
- Reliability.
- Accessibility.
- Shared components.
- Data freshness.
- Large-data rendering.
- Testing.
- Migration.

### 6. Discuss Trade-Offs

Demonstrate judgment rather than presenting one perfect solution.

### 7. Explain Rollout and Measurement

This distinguishes Staff-level responses from Senior-level responses.

## 12. Behavioral Stories to Prepare

### Story 1: Performance Improvement

Model page from 12–15 seconds to under 4 seconds.

Focus on:

- Measurement.
- Root-cause decomposition.
- Cross-stack changes.
- Business or engineering impact.
- Regression prevention.

### Story 2: Shared EngX Investment

Common health, freshness, or entity components.

Focus on:

- Identifying repetition.
- API design.
- Adoption.
- Migration.
- Avoiding a platform that was too generic.

### Story 3: Reliability Incident

A page displayed missing or late data incorrectly.

Focus on:

- User impact.
- Distinguishing unknown from unhealthy.
- Instrumentation.
- Incident response.
- Permanent guardrails.

### Story 4: Cross-Functional Disagreement

Compliance, legal, MLOps, and model owners had different definitions or ownership expectations.

Focus on:

- Clarifying decision ownership.
- Writing down contracts.
- Creating phased delivery.
- Maintaining relationships.
- Reaching a durable outcome.

### Story 5: Ambiguous Product Direction

Creating the MLOps homepage or crew-based navigation.

Focus on:

- User research.
- Information architecture.
- Prioritization.
- Prototype and iteration.
- Success metrics.

### Story 6: Team Leverage

Leading five engineers while maintaining technical depth.

Focus on:

- Delegation.
- Technical direction.
- Design reviews.
- Raising engineering quality.
- Mentorship.
- Avoiding becoming a bottleneck.

## 14. Common Weak Answers to Avoid

### Too Implementation-Focused

Weak:

> I used React, hooks, GraphQL, and memoization.

Better:

> I designed the page around the model owner’s debugging workflow, then selected React boundaries and data contracts that supported progressive rendering and isolated failure.

### Claiming Shared Components Without Adoption

Weak:

> I created a reusable table.

Better:

> I standardized filtering, URL serialization, accessibility, empty states, and analytics for data-heavy tables, migrated three surfaces, and reduced the work needed to launch subsequent pages.

### Treating Performance as Memoization

Weak:

> We added `useMemo`.

Better:

> We measured the route, removed request waterfalls, improved aggregation, reduced payloads, deferred secondary visualizations, and then profiled rendering to identify smaller client-side improvements.

### Ignoring Imperfect Data

Weak:

> The API returns the model health.

Better:

> Health came from multiple systems with different freshness and reliability. We made source, generated time, and unknown states explicit so users could judge whether the result was trustworthy.

### No Organizational Dimension

Weak:

> I built the page.

Better:

> I aligned service owners on contracts, guided the implementation across engineers, established shared components, managed incremental rollout, and defined operational ownership.

Before the interview, rehearse:

- One shared-component and EngX story.
- One frontend reliability incident.
- One accessibility example.
